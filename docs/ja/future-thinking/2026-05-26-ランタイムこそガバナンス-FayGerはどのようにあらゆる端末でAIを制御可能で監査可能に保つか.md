# ランタイムこそガバナンス：FayGer はどのようにあらゆる端末で AI を制御可能・監査可能に保つか

AI の安全性と聞くと、多くの人は最初に「モデルのアラインメント」を思い浮かべる。  
もちろん大事だが、それは全体像ではない。

AI が端末を引き継ぎ、ユーザーの代わりにソフトを操作し、組織のために公共サービスを提供しはじめると、社会を本当にパニックに突き落とすのは、モデルが一度幻覚を起こしたことではない。**システム的な制御不能**だ。  
どこで動いているのか分からない。どんな権限を渡されているのか分からない。さっき何を実行したのかも分からない。さらに、事故が起きたとき誰の責任を問えばいいのか、どう止めるのか、どう振り返るのか、どう異議を申し立てるのかも分からない。

このリスクを私は **「自由態の行動」** と呼んでいる。  
AI に自由態で動くことを許した瞬間、いかなる製品上の理屈も、「ちゃんと安全策を入れています」という一言も、次の事故で必ず突き破られる。

だから私はずっと言い続けている。**AI を放任してはいけない。人の監護のもとで動かなければならない。**  
これは姿勢のように聞こえるが、エンジニアリングに落とすと具体的な要求になる。すなわち、端末を越え、言語を越え、ベンダーを越えて一貫した「実行基盤」を持ち、監護・隔離・監査・取り消しといった能力をデフォルト値として組み込まなければならない。  
それを担うのが FayGer である。

## 1. なぜ「ランタイム」は AI 時代のガバナンス基盤になるのか

従来のソフトウェア時代、「ランタイム」は主にエンジニアリング上の利便性として理解されてきた。  
JVM は Java に「一度コンパイルすればどこでも動く」を与え、Docker はイメージを別マシンでも安定して動かし、WASM/WASI はコードをサンドボックスで動かす。

しかし Fay（iFay/coFay）の時代になると、ランタイムは単なる利便性ではなく、ガバナンス基盤になる。Fay の実行は「計算する」だけではなく、**「外に向かって手を出す」** からだ。  
メッセージを送り、フォームを送信し、端末を操作し、ハードウェアを呼び出し、決済をトリガーし、ドローンを動かす——いずれも現実への結果を伴う。

異なる端末、異なるホスト、異なるシステムコールチェーンの上で、各 Fay を「それぞれ勝手に」走らせれば、最も恐ろしい事態が生じる。  
**監護セマンティクスの断片化** だ。  
ある端末ではブレーキが効くが、別の端末では効かない。あるシステムには監査があるが、別のシステムにはログ片しかない。あるバージョンでは権限が制限されているが、別のバージョンではこっそり緩められている。

これはエンジニアリングの問題ではなく、社会の問題である。  
事故が起きたとき、責任の連鎖はまさにこうした「環境差」によって引き裂かれるからだ。

## 2. FayGer の位置づけ：JVM/Docker のように、しかし狙いは「ガバナンス可能な実行」

一言で言えば FayGer は **Fay エコシステムの仮想ランタイム環境** である。  
配布可能・ロード可能・検証可能な Fay 製品（BuF）を受け取り、異なる端末上で一貫した方法で実行する。

ただ、私が気にしているのは「動くか」ではなく「**どう** 動くか」である。  
FayGer の核となる約束は四つの語に集約される。**一貫・隔離・証明可能・観測可能。**

類比はこうだ。

- Java バイトコードに対しての JVM は、ビジネスロジックには干渉しないが、ロード・検証・実行・隔離を規定する。
- コンテナイメージに対しての Docker / OCI Runtime は、アプリの中身には干渉しないが、イメージ構造・権限・リソースクォータ・実行境界を規定する。

FayGer も同様だ。Fay の能力境界の書き方は規定しない（それはプロトコルとスキルの問題）。規定するのは、**Fay が社会へ届けられるとき、どのような「ガバナンス可能な姿」で実行されなければならないか** である。

## 3. 三層構造がなぜ重要か：Loader / Runtime / Adapter

FayGer は自身を三層に分割している。この分割はガバナンスにとって決定的である。

1) **Loader Layer（ロード層）**  
BuF と外界との境界。読み取り、構造検証、バージョン交渉、署名検証、ロード戦略（Eager/Lazy）を担う。  
ロード層を私は **「税関」** に例える。構造が合わなければ通さない。署名がなければ通さない。バージョンが合わなければ通さない。

2) **Runtime Layer（実行層）**  
BuF セマンティクスの実行者。複数言語による実装（Rust / Go / TypeScript……）が、統一インタフェースを通じて相互に置き換え可能であることを許す。  
これは見落とされがちな問題を解く。ランタイムを特定の言語エコシステムに縛れば、ガバナンス能力もある会社・あるツールチェーンに縛り付けることになり、最終的に事実上の独占に至る。

3) **Adapter Layer（適配層）**  
FayGer とホスト端末との境界。Universal Instruction をシステムコールに翻訳し、逆方向ではシステムからの応答を監査可能なイベントへと変える。  
適配層を私は **「権限ゲート」** に例える。端末がどんな能力を、どれだけ、どの粒度で渡すかは、すべてここで交渉され制限されなければならない。

三層の価値は、「ガバナンスのセマンティクス」を安定した層に置けることにある。各端末のエンジニアリングの細部に分散させない。  
ガバナンスは各チームの自覚に頼ってはならない。アーキテクチャによって強制されるべきだ。

## 4. 「制御可能」はボタンではなく、デフォルトの集合

「AI は監護下で動かなければならない」と言うとき、私が要求しているのは UI のスイッチではない。  
迂回不可能なデフォルトの集合であり、それを担うのに最もふさわしい場所が FayGer なのだ。

ランタイムのデフォルトとして固めるべきだと考える点をいくつか挙げる。

### 4.1 ケイパビリティ交渉と最小権限

端末のケイパビリティは宣言・交渉・付与されなければならない。「プログラムが呼べるなら呼ぶ」では駄目だ。  
ある BuF にファイルシステム書き込みケイパビリティが付与されていないなら、OS のなんらかの脆弱性で「ついでに書く」ようなことがあってはならない。

社会が公共サービスを coFay に依存し始めるとき、これはさらに敏感になる。  
公共的な役割の権限境界が不明確なら、効率はそのまま権力に変わる。

### 4.2 リソースクォータと暴走半径

Fay の CPU / メモリ / ネットワーク / ストレージのクォータは、本質的にその暴走半径そのものだ。  
「モデルが自分で節度を持ってくれる」を当てにはできない。ハードな境界はランタイム層で引くしかない。

### 4.3 観測可能性：監査を事故後の継ぎ当てにしない

多くのシステムでは、監査は事故が起きてから後付けされる。  
だが Fay の監査はデフォルト能力でなければならない。さもなければ責任が最後まで突き抜けない。

私が好むやり方は、ランタイムが統一されたエラーモデルと、発生レイヤーのタグおよび cause chain を持つ構造化エラーを提供すること。同時に、重要な実行イベントを、購読・集約・凍結が可能な監査ストリームとして提供することだ。  
デフォルトでは静か（誰の邪魔もしない）だが、必要になれば丸ごと取り出せる。

### 4.4 「外部への影響を止める」を最優先に

監護関係が成立していない、責任側に到達できない、システムが不確定な状態に入った——そんなときは、私は Fay を止めるほうを選ぶ。  
保守的だからではない。責任構造を尊重するからだ。  
**タスクを完了させないほうが、責任者がいない状態で外部へ手を出し続けるより良い。**

この種のポリシーが業務コードに散らばっていれば、必ず KPI に侵食される。ランタイムに置いて初めて、社会的なルールになる可能性が出てくる。

## 5. FayGer と iFay/coFay の関係：万能ではないが、「最低ラインが現場に降りるか」を決める

私は FayGer を万能だとは思っていない。  
アイデンティティ、ペルソナの境界、プロトコルセマンティクス、申し立て機構、貢献コンセンサス——それぞれに専用の層が必要だ。

しかし FayGer はもっと根本的な問いを引き受けている。  
これらの理念をドキュメントに、プロトコルに、宣言に書き込んだあと、**実際の端末に届いたときに歪まないか？** という問いだ。

Phase 1 では iFay に UI 操作をシミュレートさせる。  
Phase 2 では CAP/DTP を通じて端末を引き取る。  
Phase 3 ではリモートプロトコルでネットワークスキルを呼ぶ。  
Phase 4 では iFay と coFay を協働させる。  
Phase 5 ではポスト貨幣時代の価値分配さえ議論することになる。

しかしどの段階に進んでも、最も基本的な一文は変わってはならない。  
**AI を放任してはいけない。人の監護のもとで動かなければならない。**

ランタイムの仕事は、この「人の言葉」を「システムが回避できない事実」に変えることだ。

## 6. 結び：未来の恐れは「AI が強い」ではなく、「AI が強くて、しかもガバナンス不能」

今日、AI に対する多くの恐怖は、失業・貧困への逆戻り・意味の崩壊に向けられている。  
そうした感情は理解できる。

しかし、もし本当に生産力豊かな時代に進むのであれば、生存権が労働に人質に取られている状態から抜け出すべきだ。  
社会の安定を本当に決めるのは、ガバナンスになる。責任がきちんと突き抜けるか、申し立てに入口があるか、公共サービスに監査があるか、特権と発言権が貢献に正比例しているか。

そしてガバナンスの第一歩は、AI の実行そのものをガバナンス可能にすることだ。  
私の見立てでは、FayGer は避けて通れない地盤である。
